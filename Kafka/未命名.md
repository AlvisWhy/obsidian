#为什么还需要 `isolation.level = "read_committed"`？

因为事务中的消息在事务提交前，可能已经被写入 Kafka 的日志，但还不能被当作已提交的数据读取。
如果只有一个producer的情况
启用了幂等 Producer就可以。
假设发送消息时发生网络超时：
1. Producer 发送消息。
2. Broker 可能已经成功写入，但 ACK 丢失。
3. Producer 重试。
4. Kafka 利用 Producer ID 和 sequence number 识别重试，避免将同一次发送重复追加到日志中。

第一层：Idempotent Producer

```
producer = Producer({    "bootstrap.servers": "localhost:9092",    "enable.idempotence": True,})
```

主要解决：网络重试导致同一批消息重复写入 Kafka。原理是利用pid和

Kafka 利用 PID 和 sequence number 识别重复的发送请求，用这两个key在broker去重。

第二层：Transactional Producer

```
producer = Producer({    "bootstrap.servers": "localhost:9092",    "transactional.id": "orders-producer-1",})producer.init_transactions()
```

在幂等性的基础上，如果要处理机器重启崩溃，在其他机器也做到idempotency就增加：

- 多条消息的原子提交或中止。
    
- 稳定的事务身份，用于事务恢复与 fencing 旧实例。
    
- 配合 `read_committed`，避免消费者读取未提交事务的消息。

对比pubsub：

Kafka 的幂等性主要通过 Producer ID 和 sequence number 实现；Pub/Sub 的 Exactly-once 主要在 Subscriber 确认消息（acknowledgment）这一侧提供保证，而顺序则通过 `ordering_key` 和 Subscription 配置控制

对于 exactly once：

在创建 Pull Subscription 时开启：

```
gcloud pubsub subscriptions create orders-sub \
  --topic=orders \
  --enable-exactly-once-delivery
```

它主要依靠 Pub/Sub 分配的 `message_id` 和确认机制来保证：

1. Subscriber 收到消息并处理。
    
2. Subscriber 发送 ACK。
    
3. Pub/Sub 确认 ACK 成功后，不再向该 Subscription 重新投递同一条消息。
    
4. 如果 ACK 失败或过期，客户端需要正确处理重投和确认状态。

业务层级的idempotency(保证topic输入端没有重复的事件，后续用于去重)

加入稳定的业务事件 ID：

```
message = {    "event_id": "order-1001-created",    "order_id": "1001",    "amount": 99}
```

Subscriber 在写数据库时，可以使用 `event_id` 做唯一约束或幂等写入

对于顺序保证：
在topic设置时使用 `ordering_key` 并且 enable_message_ordering=True

```python
from google.cloud import pubsub_v1

publisher = pubsub_v1.PublisherClient(
    publisher_options=pubsub_v1.types.PublisherOptions(
        enable_message_ordering=True
    )
)

topic_path = publisher.topic_path(
    "my-project",
    "account-events"
)

future = publisher.publish(
    topic_path,
    b'{"balance": 100}',
    ordering_key="customer-123"
)

message_id = future.result()

```

```
gcloud pubsub subscriptions create account-events-sub \
  --topic=account-events \
  --enable-message-ordering
```

|需求|Kafka|Google Cloud Pub/Sub|
|---|---|---|

|保证相关消息顺序|使用相同 key 路由到同一 partition|使用相同 `ordering_key`，并启用 Subscription 排序|
|业务层防重复|业务 ID + 幂等写入|业务 ID + 幂等写入|
